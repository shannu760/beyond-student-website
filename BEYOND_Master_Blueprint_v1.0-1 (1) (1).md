# 0. Executive Summary

## Product thesis

**BEYOND is a student growth network, not another generic AI chatbot.**

Its long-term purpose is to help students answer one recurring question:

> **"What should I do next?"**

The platform begins with Class 11–12 students, especially JEE/NEET aspirants, and expands toward a broader student operating system covering:

- academic guidance
- AI tutoring
- personalized planning
- exams and performance
- student community
- study rooms
- peer learning
- scholarships
- career/course exploration
- skill development
- financial literacy
- projects
- student ideas
- verified achievements/certificates
- eventually parent/institution tools

The first strategic wedge is **decision support and academic guidance**, not trying to beat Google/Gemini or established edtech companies at generic AI tutoring.

The long-term moat is the combination of:

1. student identity and longitudinal progress
2. topic-level skill mapping
3. peer-learning network effects
4. trusted opportunity information
5. student-generated ideas and feedback
6. personalized guidance
7. a high-quality student experience

# 1. Strategic Positioning

## The problem

Students often have information but lack a system.

Common problems include:

- "Should I choose JEE or NEET?"
- "Am I preparing correctly?"
- "What should I study today?"
- "Why am I scoring poorly?"
- "Which topics should I fix first?"
- "Who can explain this to me?"
- "What happens after JEE/NEET?"
- "What does this degree actually contain?"
- "Which scholarships can I apply for?"
- "What skills should I learn?"
- "How can I turn my idea into something real?"
- "What should I do next?"

BEYOND should connect these questions instead of treating them as isolated features.

## Positioning statement

> **BEYOND is an AI-powered student growth network that helps students learn, decide, connect, build, and discover opportunities.**

## What BEYOND is NOT

- not a generic ChatGPT wrapper
- not a social-media clone designed to maximize scrolling
- not a coaching institute
- not a scholarship guarantee service
- not a trading/investment platform
- not a job marketplace for minors
- not a replacement for teachers, parents, counselors, or official authorities
- not a system that decides a student's career for them

# 2. Market Strategy

## The opening battle

Do **not** start by claiming:

> "Our AI tutor is smarter than every other AI tutor."

That is a difficult and expensive battle.

Instead:

> **"BEYOND helps students understand where they are, where they should go, and what to do next."**

AI tutoring becomes a supporting capability.

## Competitive lesson

Major edtech and AI products already provide:

- doubt solving
- personalized learning
- tests
- AI explanations
- mock exams
- tutoring
- recommendations

Therefore BEYOND's differentiation should be the **student decision + community + opportunity layer**.

## Current official-source anchors

JEE Main information should be tied to the current NTA JEE Main bulletin rather than hard-coded assumptions.

NEET information should be tied to the current NTA NEET bulletin and official notices.

Scholarship data should prioritize the National Scholarship Portal and official scheme pages, with secondary discovery sources such as Buddy4Study clearly labeled as secondary.

UGC/AICTE/NMC/university sources should be preferred for course and curriculum information.

Official sources change. Therefore all regulatory/exam/scholarship data must have:

- source URL
- source organization
- source date
- last verified timestamp
- expiry/review date
- confidence/status
- human-review flag when required

Research references:
- JEE Main official bulletin: https://jeemain.nta.nic.in/information-bulletin/
- NEET UG official portal: https://neet.nta.nic.in/
- National Scholarship Portal: https://scholarships.gov.in/
- UGC: https://www.ugc.gov.in/
- AICTE: https://www.aicte-india.org/
- Buddy4Study: https://www.buddy4study.com/

The National Scholarship Portal currently operates for AY 2026–27 and provides scholarship scheme discovery, eligibility, application/status functions, and OTR-related workflows. Use the official portal as the source of truth for official scholarship claims.

# 6. BEYOND AI — Architecture

## Principle

BEYOND should not be:

`student -> prompt -> LLM -> answer`

It should be:

`student`
→ authenticate
→ load permitted student context
→ classify task
→ retrieve trusted context
→ select tools
→ call model provider
→ validate output
→ respond
→ optionally update learning state
→ recommend next action

## AI layers

### Layer 1 — Conversation
Natural-language interaction.

### Layer 2 — Student context
Only data the student has permitted and the system is authorized to access.

### Layer 3 — Knowledge retrieval
Official curriculum, owned content, licensed/open resources, verified guidance data.

### Layer 4 — Tools
Examples:

- create study plan
- retrieve performance
- generate quiz
- evaluate answer
- find scholarship matches
- find study room
- recommend peer help
- update goal
- explain course
- create project plan

### Layer 5 — Guardrails
- age-appropriate behavior
- privacy protection
- uncertainty handling
- source attribution
- hallucination reduction
- moderation
- abuse prevention

### Layer 6 — Evaluation
Every important AI workflow needs automated evaluation sets.

# 7. Model Provider Strategy

## Never hard-code the entire product to one provider.

Create an internal interface such as:

`AIProvider`

with operations conceptually like:

- generateText()
- generateStructured()
- embed()
- moderate()
- stream()

Then provider adapters can be added later.

Potential providers can include:

- Google Gemini
- OpenAI
- Anthropic
- local/open-weight models where practical

The application should not expose provider API keys to the browser.

## Initial strategy

Use one capable provider for the MVP through a server-side adapter.

Build the abstraction from day one.

Do not attempt to train a foundation model from scratch.

## Cost controls

- model routing
- token limits
- response caching
- retrieval before generation
- small model for classification
- larger model only for difficult tasks
- usage quotas
- abuse limits
- prompt compression
- structured outputs
- asynchronous generation for expensive jobs

# 9. Guidance Engine

## Stage 1 — Exam direction

The diagnostic should evaluate:

- subject interests
- academic performance
- learning preferences
- stated career interests
- current preparation
- time availability
- motivation
- preferred work environments
- tolerance for different study patterns
- goals

Output:

### Not a verdict.

Instead:

**Current alignment**

**Evidence**

**Uncertainties**

**Recommended experiments**

**Suggested next 30 days**

Example:

> "Your current responses show stronger alignment with the engineering pathway, especially because of your interest in mathematics, physics and computing. This is guidance, not a permanent career judgment. Try the following diagnostic activities before committing."

## Stage 2 — Course explorer

For every course:

- what you study
- core subjects
- labs/projects
- typical duration
- eligibility
- admission routes
- possible careers
- further study
- skills required
- misconceptions
- related courses

Use official/current curriculum sources.

# 21. Recommended Technical Stack

## Frontend

### Next.js + React + TypeScript

Why:

- full-stack React framework
- App Router
- server/client components
- strong ecosystem
- good AI-agent compatibility
- excellent deployment path

Official Next.js documentation describes the App Router as the current file-system-based router and includes built-in TypeScript support.

### UI

- Tailwind CSS
- shadcn/ui
- Lucide icons
- CSS variables
- Framer Motion only where useful
- accessible primitives
- responsive design

shadcn/ui is especially suitable for this project because its components are copied into the project and remain directly customizable rather than being a black-box component package.

## Backend

### Start with Next.js server-side capabilities

Use:

- Server Actions where appropriate
- Route Handlers
- server-side service modules
- background jobs for asynchronous tasks

Do not create a separate microservice architecture in V1.

## Database

### PostgreSQL via Supabase

Use:

- Postgres
- Supabase Auth
- Row Level Security
- Storage
- Realtime where needed

Supabase provides Postgres, Auth, Storage, Realtime and related backend functionality, which is a strong fit for a solo founder.

## Hosting

### Vercel

Use for the Next.js application.

Vercel provides a straightforward Next.js deployment path.

## Testing

- Vitest for unit tests
- Playwright for end-to-end tests
- TypeScript type checking
- ESLint
- accessibility testing
- Lighthouse/performance checks

## Version control

- GitHub
- protected main branch
- pull-request discipline
- small commits
- feature branches

# 29. Antigravity Agent Strategy

## Rule

**One agent = one bounded task.**

Do not tell one agent:

> "Build the whole application."

That produces inconsistent architecture.

Instead:

- Agent 01 defines architecture.
- Agent 02 defines design system.
- Agent 03 builds authentication.
- Agent 04 builds profile.
- Agent 05 builds database migrations.
- Agent 06 builds AI abstraction.
- Agent 07 builds assessments.
- etc.

Each agent must:

1. read the project constitution
2. inspect current code
3. inspect the task specification
4. modify only assigned scope
5. run tests
6. document changes
7. report blockers
8. not redesign unrelated features

# 38. Coding Rules for Agents

Every agent must follow:

1. TypeScript strict mode.
2. No secrets in client code.
3. Validate all external input.
4. No direct database access from arbitrary client components.
5. Use server-side authorization.
6. Use RLS for Supabase data.
7. Do not bypass existing abstractions without documenting why.
8. Do not duplicate components.
9. Reuse the design system.
10. No random gradients or UI styles outside the design system.
11. No giant components.
12. Keep features modular.
13. Add tests for meaningful logic.
14. Do not silently change database schema.
15. Do not introduce a new dependency without justification.
16. Do not modify another agent's bounded feature unless necessary.
17. Update documentation when architecture changes.
18. Never put an API secret in `.env` values committed to Git.
19. Never expose private student information in logs.
20. Treat AI output as untrusted input.

# 49. Definition of MVP Success

Do not call MVP successful because:

- the UI looks good
- AI responds
- 1,000 people signed up

MVP success means:

> A meaningful group of students voluntarily returns every week because BEYOND helps them make measurable academic progress.

Evidence should include:

- repeat usage
- completed plans
- completed tests
- improved performance
- peer-help interactions
- study-room completion
- student interviews saying they would miss the product if it disappeared
